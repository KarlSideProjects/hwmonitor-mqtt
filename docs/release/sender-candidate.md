# Sender candidate inspection

No Sender package exists in this repository. The public entrance consists only of `release-public/README.md` and `release-public/LICENSE-NOTICE.md`; it ships no runtime or third-party components. Windows x64, Linux x64 and Linux ARM64 remain unavailable until their real artifacts and installation paths pass the release gates.

`python3 scripts/inspect_sender_candidate.py <platform> <unpacked-directory> <trusted-approval.json>` checks a deliberately narrow proposed layout. Platform is `linux-x64`, `linux-arm64` or `windows-x64`. The directory must contain exactly `sender` (ELF prefix) or `sender.exe` (PE prefix) and these nonempty notice files: `licenses/python.txt`, `licenses/paho-mqtt.txt`, `licenses/psutil.txt`, and `licenses/python-dotenv.txt`. Windows also requires `licenses/pythonnet.txt` and `licenses/wmi.txt`. The checker rejects other paths, links, common archive signatures, selected plaintext credential patterns, empty files and notices whose bytes do not match its embedded trusted hashes. The allowlist is owned by the checker, not by the candidate. The required approval JSON must be a regular file outside the candidate and contain `platform`, `source` (a lowercase 40-64 digit hexadecimal source identifier), `version` (a nonempty string), and `executable_sha256` (a lowercase 64 digit SHA-256). The executable must match that digest. A trusted builder or release workflow must supply and protect the approval independently; the candidate must never approve itself. The checker does not accept archives as input.

These filenames are a preliminary contract for test samples, not an inventory of a built package. A successful check is not release approval. Executable prefixes and a digest do not prove architecture, compilation, authorship, or absence of embedded Python or secrets. A malicious or mistakenly trusted approval can approve unsafe bytes; the approved source, version, build and final artifact still need independent verification. Matching these pinned notice bytes does not establish the completeness or applicability of notices for a future package. The checker cannot establish license compliance, archive safety after independent packaging, or detect every secret. Release maintainers must inspect real unpacked artifacts and published archives, establish provenance and all actual files and dependencies, review notices and corresponding-source duties, and revise this contract and its tests as necessary. Never publish solely because this command succeeds.

These are project lock entries, not proof that any item enters a Sender package. The selected Python runtime and Nuitka version are not fixed by a Sender build specification. Additional transitive or native components may be included by a compiler or runtime.

The current Dockerfile installs psutil, paho-mqtt and python-dotenv without pinned versions. The existing Windows installer fetches LibreHardwareMonitor 0.9.6 and PawnIO setup 2.2.0 from their upstream release URLs with fixed SHA-256 values. Those are existing installation inputs, not evidence that either will be bundled in a future release.

Before publishing each actual platform package, inventory every component and version from the final artifact, including Python, native libraries, paho, pygame if present, pythonnet and its dependencies if present, LibreHardwareMonitor, PawnIO, and build tool runtime inclusions. Obtain authoritative license texts and notices for those exact versions, determine any source and offer obligations and compatibility, and retain evidence for the actual distribution or external download method. The [Paho license notice](https://github.com/eclipse-paho/paho.mqtt.python/blob/v2.1.0/LICENSE.txt), [LibreHardwareMonitor license](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/v0.9.6/LICENSE), and [PawnIO source](https://github.com/namazso/PawnIO) are starting points, not proof of future package contents or compliance. ## Archive inspection in progress

`--archive` adds a preliminary archive boundary check using an independently supplied build record. It checks fixed paths, links and duplicates, bounded member sizes, selected secret patterns, archive and executable digests, manifest identity, compiler and runtime fields, and the PE or ELF architecture. It fails closed unless the exact compiler, runtime and notice-set fingerprint has been established in trusted code; the three exact expected descriptors are documented in the [Linux x64](linux-x64-notice-decision.md), [Windows x64](windows-x64-notice-decision.md), and [Linux ARM64](linux-arm64-notice-decision.md) notice decisions; unknown input sets remain rejected. These expected fingerprints are not observed output from a new producer. For Linux, that fingerprint also includes the trusted Dockerfile digest, which identifies the pinned base and dated package sources. The full notice and source obligations and trusted build-job production of the record remain open. All platforms require the supplied build report, pre-onefile inventory and private `--runtime-dir`, whose files and hashes are checked against the independently supplied record. The checker scans each runtime file for selected secret patterns and checks Linux ELF or Windows PE architecture, including bounded AnyCPU CLR metadata. Windows mode additionally checks checksum-bound validator and activator assets; these inputs must be produced and bound to the executable by an independent fixed-source build job. Notice hashes and Windows inventory paths are pinned to the observed v19/6cb inputs plus the three supplemental native notices, not approved as a complete license inventory. A future build needs its own inventory and provenance, even when version numbers match. Do not treat this mode as a release gate or use its historical path lists as a future inventory. Compose environment substitutions with no value or an empty default are recognized; the PVE example is exempted from the selected secret-pattern scan only at its exact pinned byte hash. Changed content is scanned normally.

The historical v16 Debian image contains five Python debug helpers. They match the exact members of [Debian libstdc++6 12.2.0-14+deb12u1 amd64](https://packages.debian.org/bookworm/amd64/libstdc%2B%2B6/download), package SHA-256 `5cd3171216d4ab0fc911cfe9c35509bf2dd8f47761c43b7f6a4296701551a24d`. Image inspection permits only those exact paths and hashes; it does not allow arbitrary Python files. This identification is not a complete image license or source-obligation review.

Both Linux architectures also require `--image-archive` and its trusted record hash. Image-layer files and image configuration are scanned for selected secret patterns. The ordered configuration diff IDs must match the SHA-256 of each uncompressed layer stream. These checks can report benign system files and cannot prove that every secret or embedded source is absent. The runtime scan ignores only exact, path-specific CPython, Paho and WMI literal contexts identified in the retained build evidence; it still scans the rest of every file. Thirteen historical v16 secret-pattern matches were byte-matched to nine exact Debian Bookworm package members using the [Debian package index](https://deb.debian.org/debian/dists/bookworm/main/binary-amd64/Packages.xz); only those exact paths and hashes are exempt. Changed files and unrecognized matches are rejected. Every future candidate needs fresh evidence and applicable source and license review.

A trusted fixed-source job can generate the private record with `scripts/create_sender_build_record.py`: it checks the tracked checkout, hashes deployment inputs from committed Git objects, compares the executable and manifest identity, checks invocation provenance, and captures the exact executable again against the private runtime inventory. The producer must supply `--provenance` from its fresh compiler and capture invocation; arbitrary caller-created provenance is not a trusted build. Keep the record outside the release asset directory and compare the checkout SHA with the selected build source. The generator does not authenticate its own execution environment or grant publication rights; its output is trustworthy only when produced and protected by the designated trusted job.

The Linux builder writes private `evidence/report.xml`, `inventory.json`, `provenance.json`, and `runtime/` from a fresh build. The Windows private workflow uses the same capture mechanism. Each capture runs the produced executable with a temporary home and a private loopback listener; incomplete or mismatched extraction is rejected. These producer changes still require native validation on each target. The approved Linux x64 descriptor does not authenticate the producer or authorize publication; artifact, source, flow and human approvals remain separate.

The private Windows package workflow checks the Microsoft x64 runtime prerequisite and runs positive native sensor, WMI, profile, and PowerShell bootstrap checks. It does not uninstall the hosted runner’s runtime: a separate ServerCore rehearsal on source `30ed72f` exercised the missing-runtime negative and installed-runtime positive paths with the `da634` fixture and the same unchanged prerequisite helper. It does not establish a clean physical host test of the `ca87` candidate. Keep separate one-off rehearsal evidence and retain the license, source, flow, and human review gates.
