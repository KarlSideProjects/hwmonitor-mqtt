# Sender release orchestration WIP

The release workflow derives a source version but does not build or stage a release. A scheduled or manual publisher job calls the drain controller in the protected `sender-release-publisher` environment; do not configure its credential or enable publication from this branch. The loopback draft staging script is a test prototype, not a GitHub publisher; it accepts only `http://127.0.0.1` and has no credential support.

A complete implementation must validate all three platform artifacts, checksums, installer scripts and independently approved legal inputs for one committed source before a draft becomes ready. The inspector under development consumes an external build record, build report, inventory, runtime directory and archive; Linux x64 also requires an image archive. Its approved notice and source fingerprints are currently empty. A passing sample inspection is not legal approval.

Versions use `0.1.<ordinal>` for a commit in the complete master first-parent history. The publisher must compare every existing release's source and tag before assigning a version; a rewritten history or collision must stop for investigation. Source-exclusive preparation is required because GitHub can allow duplicate draft tags. The current prototype does not provide this lock.

A future publisher must retain validated ready drafts before entering the serialized drain, verify remote assets and receipts, and reconcile publication and latest promotion after interruption. It must not mutate ready or published assets or move latest backwards. Scheduled and manual drains need to recover queued candidates; Actions concurrency alone is not durable storage.

Only trusted master pushes and default-ref maintenance may reach a publisher. The source repository token cannot publish to the separate public repository. Before activation, a human must provision a fine-grained credential restricted to `KarlSideProjects/hwmonitor-mqtt-releases`, with only the target release write permission needed, and make it available solely to the trusted publisher job. Build and test jobs must not receive that credential. Do not copy an existing broad credential.

Before a non-draft delivery, complete the project flow synchronization, independent review and trusted-base validation, actual platform execution and installation tests, third-party obligations and human approvals. No production release, tag, draft or secret was created by this WIP.

## Backend and activation boundary

`scripts/release_backend.py` provides the GitHub API backend; `scripts/release_controller.py` exposes prepare and drain commands. A protected controller must independently validate each platform's real build and inspector results, generate the receipt itself, and call `prepare_candidate`; an artifact cannot approve itself. The narrow receipt contains `source`, `version`, and `assets`, with each exact release asset mapped to its byte `size` and `sha256:` digest. The inspector currently outputs only exit status and text, and its `APPROVED_NOTICE_SETS` is empty: no trusted receipt is available yet.

Preparation requires native source-specific Actions concurrency. Publishing requires one global Actions concurrency group and a scheduled or manually triggered recovery drain. GitHub's `queue: max` can queue only 100 pending jobs; READY drafts must survive overflow and be drained later. A canceled push before preparation has no draft, so a recovery controller must also scan trusted first-parent master history and rebuild missing sources; the current workflow does not implement that scan. The preparation job remains disabled because trusted producer evidence is not wired; the scheduled and manual publisher runs drain READY drafts under the global lock. The controller must bind the source ordinal to complete first-parent master history and make one immutable receipt per source. It must not grant the target credential to build, test, PR, or candidate code.

For activation, integrate and verify the actual `scripts/build_sender_package.py --version <version> --output <dir>` producers on all three platforms from the same checkout, locked build dependencies, real Windows 5.1/7, Linux/PVE, and ARM execution tests. The inspector interface uses `--archive PLATFORM ARCHIVE PRIVATE_RECORD --assets PRIVATE_ASSET_DIR --build-report PRIVATE_REPORT --inventory PRIVATE_INVENTORY --runtime-dir PRIVATE_PRE_ONEFILE_DIR`, with `--image-archive PRIVATE_IMAGE` for Linux. The record and evidence must bind source, version, executable, compiler, runtime, archive and inventory; notice/source obligations and the Microsoft prerequisite remain unapproved. The ARM VM WIP artifact is evidence for its own source only, not this candidate.

A human must create a fine-grained credential restricted to `KarlSideProjects/hwmonitor-mqtt-releases` with repository contents write access, store it only in a protected publisher environment, and verify environment restrictions and trusted master/default-ref triggers before enabling the controller. Do not reuse the source `GITHUB_TOKEN` or a broader credential. Investigate identity collisions, incomplete published releases, missing asset digests, rewritten master history, and unexpected latest rather than deleting or overwriting published assets. Never manually advance latest to recover a failed candidate.

Reference: [GitHub concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) and [release API](https://docs.github.com/en/rest/releases/releases). The controlled test service is not proof of production GitHub behavior or platform/legal approval.

The release asset set also requires `install.sh` and `install.ps1` with individual checksums. The trusted controller must verify these bytes against `bootstrap.sh` and `bootstrap.ps1` at the committed source; adding their names to the checksum gate does not establish that provenance. A READY or published same-source retry reuses its saved assets; a changed STAGING retry removes the old draft assets before recording and uploading a new validated receipt. Both operations still require the documented external source-specific lock.

The WIP controller accepts a private evidence directory with one subdirectory per platform (`linux-x64`, `linux-arm64`, `windows-x64`). Each contains `record.json`, `report.xml`, `inventory.json`, and `runtime/`; Linux additionally needs `image.tar`. The controller checks the record identity, source-history version, complete checksums, and committed installer bytes, then runs the archive inspector for each platform before constructing a receipt. The merged preliminary archive inspector keeps its notice approval set empty and must be updated with the reviewed runtime corrections before release. The test-only inspector double does not authorize publication. Producer job identity and evidence origin must be established by trusted workflow wiring; an arbitrary caller-supplied record does not establish them.

`release_controller.py pending --master <full-sha> --start <full-sha> --limit <1-100>` lists an oldest-first bounded set of missing and STAGING sources from first-parent history. It verifies all existing release identities against that history and checks READY assets; history changes and inconsistent releases fail closed. This command identifies work but does not dispatch builds, so durable automatic recovery is not complete. The start commit must be a reviewed activation boundary on master.

`recover` uses the same bounded history check and dispatches each missing source to the source repository's `sender-release.yml` on `master`, using a separate `SOURCE_WORKFLOW_TOKEN` with source Actions write permission. GitHub documents that `workflow_dispatch` events generated by the source repository token create workflow runs: [GITHUB_TOKEN events](https://docs.github.com/en/actions/concepts/security/github_token). Interrupted dispatch is safe to retry only after source-specific serialization and the preparation jobs are implemented. Do not run recovery yet: those jobs are not connected and a dispatch currently stops at the version gate.
