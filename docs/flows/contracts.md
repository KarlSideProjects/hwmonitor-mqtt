# Shared distribution contracts

The Linux bootstrap resolves a latest-release tag and requires exact official asset URLs, release metadata and SHA-256 checksum records. It extracts the archive's sender and executes it to validate and stage the archive first as `nobody` and then as root. The staging interface checks a fixed member set, sizes, platform, source, version and executable digest. These checks depend on the release assets and checksums supplied together; the bootstrap does not verify an independent signature. The Windows bootstrap likewise verifies the downloaded validator, activator and ZIP against release checksum records, then matches package identity with release metadata. See `bootstrap.sh`, `bootstrap.ps1`, `hwmonitor_mqtt/platforms/sender_archive.py` and `scripts/windows/validate_sender_package.ps1`.

The Linux compiled sender exposes `--version`, `--stage`, `--pve-bootstrap`, `--install` and `--native-install`; its default entry runs the sender. `scripts/build_sender_package.py` owns this generated entrypoint and Linux candidate layout, including the generated `.dockerignore` that admits only the Dockerfile and sender to the build context. The repository root has no `.dockerignore`. The Windows package contains `sender.exe`, a manifest, notices and task scripts; `scripts/windows/package_sender.py` owns its assembly. The manifest records platform, source, version, executable SHA-256, compiler and runtime inventory. The Windows validator checks only the fields and archive properties described in its source, not an independently signed provenance record.

The installer controller in `hwmonitor_mqtt/platforms/install.py` selects the target and deployment, checks prerequisites and invokes the platform installer. Linux Docker uses Compose and an optional override; native PVE installs a systemd service and attempts to restore its previous state on failed compiled activation. The bootstraps preserve existing `.env` settings and attempt rollback of their deployment inputs; failures can retain backups and a pinned image for manual recovery; Windows activation also restores a recognized scheduled task and package when possible. PVE preparation can create a dedicated API user, token and read-only ACL and update private configuration and CA files; these changes, Docker installation, and Windows hardware driver installation can outlive failed activation. The private development `install.sh` Docker path requires a compiled `sender` at the repository root; Windows task scripts also remain developer interfaces. For native PVE, isolated onefile installation uses a private FIFO to coordinate repeated interrupts and final status; cancellation before stable service commit attempts recovery, which can fail. After stability checks the native commit ignores cooperative cancellation; successful native status commits root inputs before the marker, so a marker failure reports failure while preserving the new installation and backup. SIGKILL and power loss can interrupt recovery. Linux version identity is build-bound; Windows validates the adjacent manifest. Public bootstrap updates are manually invoked; there is no automatic updater or management service. See [installation and maintenance](../deployment/installation.md) for operating instructions.

MQTT full and ESP payloads may include `sender_version`, a three-part SemVer string or null. Linux compiled entrypoints supply their selected build version; Windows uses the validated installed manifest. Source execution may report null. Consumers preserve legacy payload compatibility and must not infer installed versions from Public latest.
